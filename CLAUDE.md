# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Mod Is

**SLO VE — "SexLab / OStim — Voices and Expressions."** ("SLO" = SexLab / OStim; "VE" = Voices and Expressions.)

A **standalone** mod - Papyrus, plus one small SKSE plugin since 0.7.0 (`SLOVE.dll`, the in-game settings menu; every voice/expression/SFX engine is still Papyrus) - that adds scene **voices** (moans + spoken dirty-talk lines) and **facial expressions** to **SexLab P+ (SexLab Framework PPLUS 2.17+; the contact-detection features need 2.19+)** scenes. Design points:

- **No MCM; one optional gameplay system.** All configuration lives in TOML files, live-reloadable in console. The optional in-game menu (see [Settings menu plugin](#settings-menu-plugin-skse)) is a front end that edits `SLOVE.toml`: the file stays the one source of truth, and the mod runs unchanged without the menu. The **willpower/resistance** mechanic is the one gameplay system kept from Hentairim; disable it in `[resistance]`.
- It is a **slim port/refactor of Hentairim/IVDT** — the source comments repeatedly say "Port of Hentairim's IVDTControllerScript / IVDTSceneTrackerScript / HentairimExpressions." The gameplay-heavy Hentairim systems (linear scenes, foreplay choreography, HugePP addiction, stage-advance timers, cum shaders) are **stripped out** and left as no-op compatibility stubs so the ported voice/expression logic stays mechanically identical. The exception is the **resistance/willpower/break** system, re-ported in full as `SLOVE_Resistance` (see the script table).
- **Mutually exclusive with full Hentairim P+** — run one or the other, not both.
- v1 is **SexLab P+ only**; an OStim backend is planned via the framework-adapter seam (see below) but not yet present.

**Hard requirements:** SKSE64, SexLab P+ 2.17+ (the physics / contact features need 2.19+ and are version-gated - see the two 2.19 gotchas below), **AudioUtil** (sibling SKSE plugin - voice playback, lipsync, TOML config API), PapyrusUtil (JSON preset data), Mfg Fix NG (all face writes).
**Soft/optional:** SKSE Menu Framework 3 (the in-game settings menu), MFEE (Mu Facial Expression Extended), sr_fillherup (tongue armors), Devious Devices (gag), SexLab Survival (`_SLS_AhegaoStateChange`), SOS/TNG (huge-partner detection), Accurate Penetration via AudioUtilPPA (measured penetration/gape).

## Build

**No `.vscode` folder.** Build config is `SLOVE.ppj` (Pyro project), `skse/xmake.lua` (the plugin) and `scripts/build.ps1`, which drives both. Always build through `build.ps1`, never with a bare `xmake` or Pyro run.

**After any big change, run `docs/smoke-test.md`** — §1–§8 are AI-executable checks (full rebuild, API sync, firewall grep, channel hygiene, TOML parse, config-key sync, BSA/asset path verification); §9 is the in-game handoff list to give the user.

**On every release, run `docs/use-cases.md`** — the functional regression matrix (one row per user-facing feature: voices, expressions, SFX, integrations, resistance, robustness), split into AI-checkable evidence vs. user in-game confirmation. Two obligations, both required before tagging:
1. **Check for regressions.** Walk the matrix, verify every AI-checkable row still passes, and hand the user the in-game rows to confirm. Do not call a release verified until the audio/visual rows get a human yes (or an explicit waiver).
2. **Keep the matrix current.** If the release added or changed a user-facing feature, add or update the corresponding use case(s) in `docs/use-cases.md` in the same release — a feature with no row is an untested feature. Removed features lose their row.

```
powershell scripts\build.ps1        # run from repo root
```

`build.ps1` (no arguments = everything; the mod's ONE version is `fomod\info.xml`, read at the top):
1. `scripts\check-config.ps1 -WriteDefaults`: the settings sync check (see the gotcha "A setting lives in four places"), which also regenerates `dist\SKSE\Plugins\SLOVE\SLOVE.defaults.toml`.
2. `Build-Plugin` (full build only): `xmake` in `skse\` with `--slove_version=<version>`, then `core-tests` against the shipped `SLOVE.toml`, then asserts (the DLL in `dist` is the one just built, its file version is the mod version, x64, no stray install folder).
3. `Build-PPlus`: mirrors `papyrus\Source\*.psc` into `dist\Scripts\Source\`, runs Pyro on `SLOVE.ppj`.
4. `Build-Classic`: derives `SLOVE-classic.ppj` and compiles `papyrus\classic\Source` into `dist-classic`.
5. `Assert-VariantTypes`, then `Build-Fomod`: stages `Release\FOMOD`, checks that `Core` holds `SLOVE.dll`, the menu schema and the defaults (and no `.pdb`), and writes `Release\SLO_VE_v<version>.zip`.

Switches: `-Variant PPlus|Classic` (that script set only, no plugin, no FOMOD), `-NoFomod`, `-NoPlugin` (scripts without the C++ toolchain; refused when a FOMOD would be packaged).

## Framework Adapter — the firewall rule

`docs/framework-adapter.md` defines the seam that makes a future OStim backend possible. **This is a hard invariant — preserve it in every edit:**

- **`SLOVE_Director` is the ONLY script allowed to reference `SexLabFramework` / `SexLabThread` / `SexlabRegistry` or SLPP mod-event names.** `SLOVE_Voice` and `SLOVE_Expressions` talk **only** to the Director's API and `SLOVE_*` events. An OStim backend would be an alternative director (`SLOVE_DirectorOStim`) with the same API surface + a replacement `SLOVE_Hentairim_Tags` (labels are annotation-scheme-specific).
- **SLOVE-owned mod events** (re-broadcast by the Director, framework-independent): `SLOVE_SceneStart`, `SLOVE_StageStart`, `SLOVE_Orgasm`, `SLOVE_SceneEnd`. Third-party event consumed raw: `_SLS_AhegaoStateChange` — by Expressions (pause face writes) **and** the Director (sets the `SLOVE_FaceOwnsMouth_SLS` StorageUtil marker on the player so `PlaySound` plays PC moans with `blockLipSync=true` and they don't lipsync over the SLS face; re-seeded from the `_SLS_IsAhegaoing` key in `Maintenance()`). The face-owns-mouth marker is the union of the Director's SLS flag and Expressions' `SLOVE_FaceOwnsMouth_Expr` flag, read per line in `PlaySound` via `FaceOwnsMouth()` — AudioUtil has no standing per-actor lipsync block.
- **Director API consumed by Voice/Expressions** (thin pass-throughs so consumers never touch `SexLabThread`): `GetPositions`, `GetPositionIdx`, `GetEnjoyment`, `GetTimeTotal`, `HasSceneTag`, `IsSubmissive`, `GetActiveSceneId`, `GetStageNum`, `GetStagesCount`, `GetGender`/`IsMale`; label getters `GetStimulationlabel`/`GetPenisActionLabel`/`GetOralLabel`/`GetEndingLabel`/`GetPenetrationLabel`; latches `GetDirectorLastLabelTime`/`GetDirectorLastPhysicsLabelTime`; lifecycle `AnimationisEnding`, `isUpdating`, `SceneisIntense`, `IsHugePP`, `PlaySound`.
- **Documented acceptable leaks:** `SLOVE_Hentairim_Tags.HasASLTag` calls `SexlabRegistry.IsSceneTag`; `GetLegacyStageNum` uses `SexlabRegistry.GetAllStages`.

## AudioUtil Relationship (deep, load-bearing)

SLO VE is a thin Papyrus layer over the **AudioUtil SKSE plugin** (sibling repo `c:/Playground/Skyrim/mods/AudioUtil`). **AudioUtil owns all audio + config-file reading + slot resolution + lipsync + the penetration bridge; SLO VE decides *what category* to play *when* and hands it an actor.**

- **Voice playback:** `SLOVE_Director.PlaySound` → `AudioUtil.Play(category, actor, wait, 1.0, group, channel)`. AudioUtil resolves the actor's **voice slot** (voicetype/race/NPC-override). SLO VE ships **no Sound forms and no voice aliases**.
- **Body SFX:** `SLOVE_SFX` calls `AudioUtil.PlaySFX(name, actor, 1.0, "sfx", channel)` — names resolve as categories of the preset's **`SFX0` slot** (`sex = "all"`; audio under `Sound\fx\SloveSFX`), which AudioUtil checks before the flat `[sfx]` table; channels `sfx_main_<pos>` / `sfx_contact_<pos>` keep each actor's stream and one-shots from cutting each other off.
- **Config API:** `SLOVE_Config` reads all settings through AudioUtil's **TomlUtil** (`TomlUtil.GetInt/GetFloat/GetString/GetBool/Reload/GetAPIVersion`).
- **Ducking/volume:** `SLOVE_Voice` calls `AudioUtil.DuckGroup/UnduckGroup/StopGroup/SetGroupVolume` for the four voice groups `pc_low`, `pc_high`, `partner_low`, `partner_high`.
- **Measured penetration (AudioUtilPPA):** `SLOVE_Expressions` calls `AudioUtilPPA.IsConnected/GetContext/GetDepth` — when the Accurate Penetration bridge is tracking an actor, penetration checks use **measured** state (context bitmask 1=vaginal, 2=anal + nonzero depth) instead of authored labels.
- **Diagnostics:** `SLOVE_Test` uses `AudioUtil.CategoryExists/PlayVoiceFromSlot/GetSlotForActor`.
- **Menu freeze:** `SLOVE_Voice`/`SLOVE_SFX` each hold their `OnUpdate` cycle and drop queued lines while `AudioUtil.IsGamePaused()` (API v7) is true — their local `GamePaused()` helper, which probes `GetAPIVersion() >= 7` once and is inert on older AudioUtil. ImGui overlay menus (SKSE Menu Framework) freeze the scene with `Main::freezeTime` **without** entering menu mode, so the Papyrus VM keeps ticking and the engines used to walk on to the next voice line / slap over a frozen animation; vanilla `Utility.IsInMenuMode()`, `Utility.Wait` and `RegisterForSingleUpdate` all miss that freeze. A line already playing is left to ring out.
- **Voice-slot preset (two files):** AudioUtil merges a base `AudioUtil.toml` then every `config\*.toml` overlay, with **globals base-only** (see the gotcha below). SLO VE therefore splits its preset in two, both under `SKSE\Plugins\AudioUtil\` (**install SLO VE last** so its base wins): `AudioUtil.toml` = the **globals only** (`[general]`/`[ppa]`/`[lipsync]`/`[gag]`), and `config\SLOVE_voices.toml` = **all the voice content** — the actor→slot routing (voicetype/race maps, category aliases, `[male_only_remap]`, fallbacks, `[groups]`) *and* every `[[slot]]` including the `SFX0` sfx slot. Keeping routing next to the slots it references makes "give this follower her own voice" a one-file edit. Female scheme: **F0/F0B = stock moan slots** (SexLab's own `vFemaleMoan01`/`03` via per-category folder refs into `Sound\fx\SexLab`; F0 is `default_female_slot`), **F1 = player pack slot**, **F2/F3 = partner/follower pack slots** — the pack slots scan `Sound\fx\SLOVE\F<n>` and backfill per-category from the stock slots via the slot `fallback` key, so any Hentairim-convention pack dropped in just works. Plus M1–M8 (bundled Hentairim male packs), C1–C10 (creatures from vanilla BSAs; `sex = "all"` so they resolve regardless of the creature's reported sex).

## Settings menu plugin (`skse/`)

`SLOVE.dll` (since 0.7.0; the same code was tagged `v0.6.29` for an hour before it was renumbered) puts one page per `SLOVE.toml` section into the Mod Control Panel of **SKSE Menu Framework 3**. It ships in the FOMOD `Core` for both variants; the framework is optional, and without it the DLL loads, logs one line and does nothing. It has no Papyrus natives, no ESP record and no save data, and it does not link against the framework or AudioUtil (both are reached at run time).

| Path | Role |
|---|---|
| `skse/xmake.lua` | Target `SLOVE` (shared, `commonlibsse-ng.plugin` rule, toml++) and target `core-tests` (the pure core + `tests/`, no game). The version is the `--slove_version` option `build.ps1` passes |

| `src/core/ConfigDoc` | One TOML file: parse, list scalars in file order, and `Rewrite`: read, splice and write through ONE exclusive handle (nobody is half-way through saving the text we edit, nobody reads ours half-written; no temp file + rename, so MO2 keeps the file in its mod folder). Each edit stands alone (`Written` / `Kept` / `Refused`), and before anything is written the result must parse and every key that was not edited must read as before. Where `TomlEdit` refuses an existing value because its line holds non-ASCII text (it maps a toml++ code-point column straight to a byte), `ReplaceByCodePoints` makes the same splice with the columns counted properly |

"add" never overwrites a key that appeared meanwhile (`Edit::ifMissing`) |

| `src/Bridge` | The only code that talks to the game: SKSE tasks that dispatch the Papyrus natives `TomlUtil.Reload` and `AudioUtil.SetGroupVolume` (live volumes). The reload is a state, not an event: it is owed until a call that started after the last write is answered with true; an unanswered call (VM reset by a load) is re-sent, a refused one (file does not parse) after a 5 s pause, never every frame |

Rules that are easy to break:

- **The DLL must never take the game down.** No `report_and_fail`, `try/catch` around every framework callback and every SKSE message, and a step that fails only switches the menu off. `SKSE::Init(a_skse, false)`: with its default `true` CommonLib sets up a second logger, unguarded, inside a `noexcept` function. It is a convenience on top of a mod that runs without it.
- **ImGui only inside a framework callback, and only through `Ui.h`.** The header's wrappers call `GetProcAddress` results without a null check, so `Env.cpp` probes every export the menu reaches before any page is registered (`kFrameworkExports`). Call a new ImGui function = add its export to that list; `check-config.ps1` compares the two. Do not read ImGui structs (`GetStyle`, `GetIO`): their layout follows the framework's ImGui version, not the header's.
- **Menu callbacks touch the model, the files and the task queue, nothing of the game.** Every engine or Papyrus call goes through `Bridge` onto the SKSE task queue; the result functor touches atomics only. File I/O happens before the first or after the last ImGui call of a frame (`Flush`).
- **A row is written when it differs from the saved value and its widget is no longer active**, and any changed row that is not drawn in a frame (page switched, group collapsed, menu closed) is written at once. A value the file refused is tried again every 2 s while the menu is open, not every frame. Flags are written as ints `0`/`1` by convention, never TOML booleans (TomlUtil's getters convert where nothing is lost - `true` reads as 1, `60.0` as 60 - and hand back the fallback otherwise, e.g. `60.5` read with `GetInt`). An int key someone wrote as a float keeps its int control and is written back as an int on the first edit. A float is re-rounded only on a real edit.
- **The file is always right; only AudioUtil's cache can lag.** TomlUtil caches the parsed file with no timestamp check, so a write is followed by `TomlUtil.Reload`. A lost dispatch (VM reset by a load) is re-sent from `kPostLoadGame` and on the next menu frame.
- **The install trap.** The CommonLib plugin rule runs `xmake install` after every build, into `%XSE_TES5_MODS_PATH%\<target name>`: with that variable set (it is on this machine, for AudioUtil) a bare build would create `E:\nefaram\mods\SLOVE` in the live MO2 folder, next to the real `SLO VE`. Three guards: `on_config` re-points the install dir into `skse\build`, an empty `on_install` replaces the rule's, and `build.ps1` scrubs the variable for the child and fails if the folder appears.
- **Deploying:** `dist\SKSE\Plugins\SLOVE.dll` goes with the rest of `dist`. The deployed `SLOVE.toml` now holds the user's menu edits: compare before overwriting it.

## ESP Plugin

`dist/SLOVE.esp` is **ESL-flagged** (ESP-FE), authored externally via **houseCARL** (not by the build). Masters: Skyrim.esm, Dawnguard.esm, Dragonborn.esm, SexLab.esm. Records:
- **Quest `SLOVE_MainQuest`** (`0x804`) with two player-forced ReferenceAliases: **alias 0** carries `SLOVE_Director` (and is the one `SLOVE_Resistance` self-acquires as `MasterScript` via `GetAlias(0)` — do not renumber it); **alias 1** (`ThreadHookAlias`, `ForcedReference` = PlayerRef `000014:Skyrim.esm`) carries `SLOVE_ThreadHook` with **no properties** (the hook self-resolves the Director). Both fill at game start (start-game-enabled → `dist/Seq/SLOVE.seq`; regenerate the SEQ if the master list ever changes — the stored prefix shifts). The alias-script bindings live in the quest's `VirtualMachineAdapter.Aliases` (a `QuestFragmentAlias` per alias whose `Property.Alias` = the alias ID).
- **Four spells at fixed FormIDs**, each holding an ActiveMagicEffect: `0x800` → Expressions spell (`SLOVE_Expressions`, ME `0x801`), `0x802` → Voice spell (`SLOVE_Voice`, ME `0x803`, whose `SceneTrackerSpell` points at itself), `0x805` → SFX spell (`SLOVE_SFX`, ME `0x806`), `0x808` → Resistance spell (`SLOVE_Resistance`, ME `0x807`). Resolved at runtime via `Game.GetFormFromFile(..., "SLOVE.esp")` — **not CK-filled properties.** Changing these FormIDs in the ESP breaks the scripts. The resistance ME carries **no filled script properties** (the effect self-acquires `MasterScript`/`SexLab` at runtime); the other three have CK-filled `MasterScript`/`SexLab`.
- **No MCM quest.** The in-game settings menu is the SKSE plugin, not an ESP record, so the ESP is untouched by it.

## Gotchas & Non-obvious Details

- **Edit sources in `papyrus/Source/`.** `dist/Scripts/Source/` is a build-generated mirror (`build.ps1` overwrites it).
- **NEVER break save loading — do not change the STRUCTURE of a live script mid-playthrough.** These scripts are attached/persistent in the player's save: `SLOVE_Director` (on the `SLOVE_MainQuest` PlayerAlias) and `SLOVE_Expressions`/`SLOVE_SFX`/`SLOVE_Voice`/`SLOVE_Resistance` (ActiveMagicEffects on scene actors). Removing or renaming a **script-level variable**, deleting a **function** (especially one containing `Utility.Wait`/`RegisterForUpdate` — a save can hold a *suspended call stack* inside it), or **changing a function's signature** (adding/removing params, even optional) makes an existing save **fail to load / hang** — no CTD, no crashlog. This actually happened (the tongue rework deleted `EquipTongueBase`/`WaitForTongueNode`/`HideTongueNode` + var `FHUTongueNodeName` and re-signatured `DirectorEndScene`). Rules: **only ADD** members to these scripts; to retire a function, keep it (byte-identical, uncalled) rather than delete — see the `SAVE-COMPAT ONLY` block in `SLOVE_Expressions`; to pass new per-call state, use a **script-level bool** (e.g. `SkipTongueRemovalOnce`), never a new function parameter. Changing a function's *body* is fine. Adding new variables/functions/events is fine. When a structural change is truly unavoidable, it is a **breaking change** requiring a clean save / new game — call it out explicitly, never ship it silently. Local variables inside functions are free (not serialized).
- **Two script variants — fix BOTH.** SLO VE ships two script sets that differ **only** in the six framework-facing scripts (`SLOVE_Director`, `SLOVE_Voice`, `SLOVE_SFX`, `SLOVE_Expressions`, `SLOVE_Resistance`, `SLOVE_Hentairim_Tags`): the **P+** copies in `papyrus\Source` (default → `dist`) and the **classic** copies in `papyrus\classic\Source` (SexLab SE 1.63 + SLSO → `dist-classic`, packaged as the FOMOD's `ClassicScripts` override). When you change any of these six, apply the same fix to **both** variants — any change to framework-agnostic logic (bug fixes, new categories/labels, behavior tweaks) must land in the P+ *and* the classic copy so the two never diverge; only genuinely framework-specific code (SexLab P+ vs classic-SexLab/SLSO API calls) should differ between them. The other four scripts (`SLOVE_Config`, `SLOVE_Log`, `SLOVE_Test`, `SLOVE_VoiceCategories`) are framework-free, live only in `papyrus\Source`, and ship to both. **`SLOVE_ThreadHook` is a seventh variant-specific script but a special case** — it exists in both trees (so the shared ESP alias binds), but the two do NOT track each other: P+ is the real `SexLabThreadHook` blocking hook, classic is an inert `ReferenceAlias` stub (see its script-table row). Don't try to "sync" them — the divergence is the design. After such an edit, rebuild both with `scripts\build.ps1` (no `-Variant` = both) and check `git diff` covers both trees.
- **Broken-willpower gameplay effects are P+-only; classic keeps broken voice/face only.** The `[resistance]` keys `brokenblockenjkeys`/`brokenpartnerenjmult` (enjoyment-key block + partner enjoyment-rate bonus, `SLOVE_Resistance.EngageBrokenEffects` + the Director's `BlockEnjoymentKeys`/`RestoreEnjoymentKeys`) exist only in the P+ variant: they drive SexLab P+'s native enjoyment game (`Config.GameEnabled`, `ModEnjoymentMult`), which classic SexLab lacks — classic's equivalent is SLSO's own minigame with a completely different key/enjoyment mechanism. Intentional framework-specific divergence like the tongue gate below — do **not** "sync" it into `papyrus\classic`.
- **Tongues are P+-only; classic gates them off.** The contact tongue (shown during cunnilingus/blowjob) depends on SexLab P+'s live oral-contact detection (2.19's NiSurface detector → the `CUN`/oral collision flags). Classic SexLab SE 1.63 has no such detector, so a tongue there could only be timed from coarse authored tags (pops at stage boundaries, misses real contact) - worse than none. The classic variant therefore hardcodes a no-op at the top of `AddTongue()` (`SLOVE_Expressions`) and `DirectorSceneStarting` (`SLOVE_Director`) - body-only gates, functions kept for save-compat - so **no tongue armor is ever added on any actor (player or NPC → no outfit-AI redress)** and neither morph nor armor tongue is shown. This is an intentional framework-specific divergence, NOT drift: the shared `expressions.enabletongue` config key is honored only by the P+ variant. **Ahegao is unaffected** - `MFEEAddAhegao` is driven by the broken/orgasm path (framework-independent) and carries its own tongue-out, and it already blocks `AddTongue()` anyway; classic keeps full ahegao. The retired `EquipTongueBase`/`WaitForTongueNode`/`HideTongueNode` block stays byte-identical (SAVE-COMPAT ONLY, uncalled - no redress).
- **Beast races wear fitted copies of the tongues, picked by race (since 0.7.1, untested in game).** A Khajiit's front teeth sit about 3 units further forward than a human's and an Argonian's about 5 forward and 2 higher (measured on the vanilla mouth head parts in head-bone coordinates), so the human-fitted tongue came out through the underside of the jaw. `SLOVE.esp` therefore has 30 tongue addons: `SLOVE_TongueAA{N}` (`000809`-`000812`, DefaultRace + 24 human / mer races), `SLOVE_TongueAA{N}_Khajiit` (`000820`-`000829`, KhajiitRace + KhajiitRaceVampire) and `SLOVE_TongueAA{N}_Argonian` (`00082A`-`000833`, ArgonianRace + ArgonianRaceVampire), and each tongue armor lists all three. A race must be in exactly ONE of them: the four beast races were taken off the standard addons, and an actor matching two addons of one armor is the double-tongue case. The beast meshes are GENERATED by `tools\tonguefit\fit_tongues.py` from the standard ten and tracked in git: never hand-edit them, change the offsets in `FITS` (head-bone coordinates: right, forward, up) and rerun. The script moves no vertex; it shifts the `tong1 1` node (the chain root HDT-SMP clones under the actor's head bone) and the head bone's bind translation by the same amount, and proves per file that every vertex moves equally through every bone. The offsets (Khajiit 0 / 3.0 / 0.55, Argonian 0 / 5.0 / 2.2) are measured, not tuned in game, and vanilla-shaped: a head replacer with a different muzzle needs its own numbers. Two things to keep in step when the tongue set changes: `SLOVE_UBE_Support.esp` overrides the ten tongue ARMOs and an override replaces the whole Armature list, so it must repeat every base addon plus its own (see `optional\UBESupport\README.md`); and `build.ps1` fails when `SLOVE.esp` names a tongue mesh `dist\meshes` does not hold. Which of the ten models an actor wears is the script's choice (`SLOVE_Expressions.GetTongueType`): `expressions.tonguetype` (default 1 = every actor wears model 1; 0 = random per actor), overridden for the four beast races by `expressions.tonguetypekhajiit` / `tonguetypeargonian` when they are 0 or more (`BeastTongueType`, default -1 = follow), and by a named `NPCTongue.json` entry for an NPC. An actor who already carries one of the ten keeps it for the scene (`CarriedTongue`): the function runs again on a mid-scene re-init, and a re-rolled model would no longer be the one `RemoveTongue` knows.
- **The tongues have BodySlide projects of their own (since 0.7.1), all generated.** `tools\tonguefit\make_bodyslide.py` writes `dist\CalienteTools\BodySlide` (30 sets: model 01-10 for the human, Khajiit and Argonian meshes, groups *SLOVE Tongues* / *... Khajiit* / *... Argonian*) and `optional\UBESupport\CalienteTools\BodySlide` (10 UBE sets, staged with the UBE option). They exist because the projects for the original tongues (HALOS Tongueslide, Fill Her Up's) build into `meshes\morten\lingas` with slot 55 and never reach SLO VE's slot-44 copies. Every base nif under `ShapeData` is the mesh it rebuilds plus a PREVIEW TRANSFORM, and the 14 sliders (move 3 units, sizes 30%, tilt 15 degrees at 100%) are OUR data, computed from the vertices: no third-party slider file is shipped, and none may be added without permission. The three sets of a model share one `.osd` because the beast copies differ from the human mesh in bone and bind data only. Rerun the script after ANY change to a tongue mesh (`fit_tongues.py` offsets included); `build.ps1` runs both scripts with `--check`. A slider moves vertices, not bones: the big beast offsets belong in `fit_tongues.py`, the sliders are for the last unit of fit. The preview transform is the 13 floats at the top of NiSkinData ("global to skin"): the game ignores them (a vanilla head carries (0, 1.55, -120.34) there, the mouth part beside it carries none, both render on the head bone), but Outfit Studio places a shape by them. The tongue meshes carry none, so beside an imported head OS drew the tongue from raw coordinates, about 1.5 units too low and without the Khajiit / Argonian shift (which lives in bones and binds). `with_preview` writes the transform that draws the tongue where the game will: its head bind plus where a head mesh is drawn (`HEAD_AT`; vanilla-style heads and UBE / High Poly Head agree to 0.15). Only the ShapeData copies get it, never the shipped meshes; a BodySlide build carries it into its output, which is why it must stay something the game ignores. Verified outside the game by a headless batch build with BodySlide 5.7.1 (`BodySlide x64.exe --groupbuild "<groups>" --targetdir <dir> --preset <name>` in a copy of the program folder): all 40 sets built, every vertex moved by exactly the preset, rig and slot unchanged; a zero preset gives the shipped geometry with BodySlide's own block order. BodySlide races on creating a missing output folder in a batch build (two of 40 sets failed once): a second build, or an existing folder, cures it. An Outfit Studio *Save Project* is the trap of the preview: it rewrites the `.osp` it was loaded from (the tracked one, when the project was opened from `dist`), writes the set's base nif with the imported head inside into the ShapeData folder it runs against (the live mod folder under MO2) and adds an `.osd` named after the set to the BodySlide output mod. The `--check` in `build.ps1` stops a release on it; undo with `git checkout` on the `.osp` and a redeploy of `CalienteTools`.
- **UBE tongues are race-specific addons, not a script branch (since 0.6.28, untested in game).** The FOMOD's UBE option (`optional\UBESupport`, staged by `build.ps1`) ships ten UBE-fitted meshes under `meshes\!UBE\SLOVE\tongues` plus `SLOVE_UBE_Support.esp`, which gives each tongue armor a SECOND Armor Addon (`SLOVE_TongueAA{N}_UBE`, the 18 `UBE_AllRace.esp` races only, priority 10, appended after the standard addon). The engine picks the addon by the wearer's race, so `SLOVE_Expressions` keeps equipping the same ten armors and must not grow a UBE check. Never add UBE races to the standard addons (`SLOVE_TongueAA1..10`, what the option did up to 0.6.27): an actor matching both addons is the double-tongue case. The UBE meshes have no body-part partition (plain `NiSkinInstance`), so slot 44 is set in the records only. Details and the rebuild recipe: `optional\UBESupport\README.md`.
- **The P+ variant runs on SexLab P+ 2.17+; only its physics paths need 2.19, and they speak the 2.19 interaction API alone (API since 0.6.26, version gate since 0.6.27).** P+ 2.19 (the NiSurface rewrite) renamed and re-indexed everything the physics paths read. SLO VE carries no 2.18-shaped calls, so on P+ 2.17 / 2.18 those paths are switched off rather than ported and the scene runs on its labels (the next gotcha is the gate). What the 2.19 API means in the code, wherever it is live: (1) `GetInteractionFlags(actor)` returns **27** flags in the order of the C++ `InterType` enum (`src/Thread/Interaction/Interaction.h` in the SexLabpp repo is the truth; the scripts index it with literals + a name comment, e.g. `f[24] ;pVaginal`). (2) Partner and velocity lookups are keyed by the actor's **own** flag - `GetPartnerByInteractionType(actor, ownFlag)`, `GetInteractionVelocity(actor, partner, ownFlag)`, `none` partner = fastest across partners - so there is no giver/receiver argument order. One caveat: upstream master's `SexLabThread.psc` property names had HandJob and FootJob swapped against that enum (SexLabpp PR 77, open as of 2026-10-05); SLO VE's literals `f[10] ;pHandJob` / `f[8] ;pFootJob` follow the C++ side, so re-check them if that PR is resolved by changing the C++ order instead. (3) Velocity is a **non-negative speed**, low-pass filtered over ~0.25s; the sign flip that marked a thrust reversal no longer exists, which is why `SLOVE_SFX` paces thrust sounds by integrating speed (`AdvanceThrust`) instead of detecting reversals. Rate follows the animation, phase does not. (4) `director.physicsfastvelocity` (18) and `sfx.thruststroke` (16) are **estimates never calibrated in game** - the `Physics speed` / `Thrust beat` printdebug lines exist to tune them. (5) `pOral`/`pHandJob`/`pFootJob` mean "genital", not "penis", so the `HasPenis` gate in `ApplyPhysicsLabels` stays. None of these members exists on P+ 2.18 or older, which the build still supports: the next gotcha is what keeps them from ever being called there.
- **One P+ build serves P+ 2.17+: every 2.19-only call is version-gated (since 0.6.27; the same shape as Apropos2's `Apropos2SLPP.IsActive` / `HasLiveData`).** `SLOVE_Utils.HasInteractionAPI()` is `SKSE.GetPluginVersion("SexLabUtil") >= 0x02130000` (P+ packs `major<<24 | minor<<16 | patch<<4`, so that is 2.19.0). Papyrus binds a member call when it is **dispatched**, not when the script loads, so a 2.19-only call that is never reached costs nothing on an older P+, while a reached one logs `method not found` on every poll. Exactly three members are 2.19-only: `GetInteractionFlags`, `GetPartnerByInteractionType`, `GetInteractionVelocity`. `IsInteractionRegistered` exists on 2.18 too **and returns true there**, which is why it cannot be the gate by itself. `SLOVE_Director`, `SLOVE_Expressions` and `SLOVE_SFX` each have an `InteractionsLive()` helper (probe first, then `IsInteractionRegistered`) and every one of those calls sits behind it; the two SFX velocity reads are guarded by `FuckingPartner`, which only the gated `UpdateFuckingPartner` sets, and `SLOVE_SFX.InitializeConfigandForms` zeroes `usevelocity` / `useadaptivevelocity` below 2.19 because the velocity loops play nothing without speed data (the label loop paces instead). Below 2.19 the P+ build therefore behaves like classic for physics: stage tags only - no physics labels, no thrust-paced SFX, no insertion / kiss / oral one-shots - while `SLOVE_SFX.ProcessLabelEdges` (a label-derived penetration edge, as in the classic variant; it shares `PenetrationEdge` / `PlayPullOutGape` with the contact-flag path and finds the receiver on the effect's OWN thread, never through the Director, whose labels are the player's scene) keeps the insertion-trauma deposit and the PPA pull-out gape. That fallback is keyed on the P+ VERSION on purpose, not on `InteractionsLive()`: on 2.19 the detector registers after the scene starts, and running the label edge until then would deposit trauma twice. One deliberate difference from classic: the tongue is NOT gated off, it is timed by the authored `CUN` / `RIM` labels alone (`IsOralTongueActive` returns on those before it reaches the gate). The probe is taken once per scene / load into a `HasInteractions` script bool in each of the three scripts, not per poll, and the Director logs one `has no contact-detection API` line per load. **Adding a 2.19-only call? Put it behind `InteractionsLive()`** and run `scripts\check-pplus-compat.ps1` (smoke test §3a: gate audit + a compile against the older headers with only the three functions stubbed). The pre-2.19 detector code of 0.6.25 is gone, not gated - an older P+ gets tags, not the old physics.
- **Thrust sounds have three sources, best first: PPA depth, P+ 2.19 contact speed, scene labels (since 0.6.28).** `SLOVE_SFX.RunPPAThrustSFX` polls `AudioUtilPPA.GetDepth` on the actor's receiver every `sfx.velocitypoll` and runs a hysteresis turn detector (`PPAThrustStep`, `sfx.ppathrustturn`): the depth turning at its peak is the impact, turning at its trough is the re-entry - the two events 0.6.25 read off the signed P+ velocity that 2.19 removed. The whole block (from the `thrust sync from PPA depth` banner through `RunPPAThrustSFX`) reads NO SexLab data and is byte-identical in `papyrus\Source` and `papyrus\classic\Source`: edit both together. It is tried first in `OnUpdate` and returns false (so the old chain runs) when PPA is not connected, `sfx.usevelocity` or `sfx.useppathrust` is off, the labels name no receiver, or PPA shows no depth for 1.5 s; that verdict sticks until the next stage (`PPAThrustNoData`). Limits: `GetDepth` is the receiver's deepest partner, so two partners on one receiver share one signal; polling adds up to one poll of lag; `ppathrustturn` (1.0) is an estimate never calibrated in game. PPA plays thrust sounds of its own, so a user hears both sets unless they silence one (the FOMOD's silent-SFX option, or PPA's `[SoundEffects] Enabled`). Moving the detection into the AudioUtil DLL (per-frame, per-partner, one event per thrust) is the known upgrade path, not done.
- **The Director is the framework firewall** — never add SexLab/SexlabRegistry/SLPP calls to Voice or Expressions (see [Framework Adapter](#framework-adapter--the-firewall-rule)).
- **Spells resolve by hardcoded FormID** (`0x800`/`0x802`/`0x805` in `SLOVE.esp`) at runtime, not via CK properties — changing those FormIDs breaks the scripts.
- **AudioUtil is a hard build-time AND runtime dependency**; the config layer fails open if its DLL is absent.
- **Preset split follows AudioUtil's base-only-globals rule.** AudioUtil reads global sections (`[general]`/`[ppa]`/`[lipsync]`/`[gag]` toggles) **only from the base `AudioUtil.toml`** — an overlay that sets them is ignored + warned. That's why the base `AudioUtil.toml` holds **only** the globals, and every additive section — the routing/category maps, `[groups]`, and all `[[slot]]`/`[sfx]` content — lives together in `config\SLOVE_voices.toml`. `[gag].keywords` is additive so it *could* move too, but is kept with the rest of `[gag]` in the base for readability. The preset sets **no `voice_root`/`sfx_root`** — every slot `path` and every `[sfx]` value is a full `Sound\...` path, so nothing depends on a shared root global.
- The **ESP is authored/edited through houseCARL**, outside the Pyro build.
- **`tools/packcheck` is the audit for the bug class above.** It parses every `PlaySound(` in `SLOVE_Voice.psc`, replays AudioUtil's resolution (literal -> alias -> category-fallback ladder -> fallback-slot chain, including the `CategoryExists` gate on the VarB remap) against a real pack's folder list, and reports beats that leave the pack while a same-beat folder sits there, plus folders nothing can ever request. Run it after touching a call site, a category name or the category maps: against the pre-0.6.15 config it surfaces 12 of the 13 mismatches; against the current one, none. It is LEXICAL - a semantic rename (`CameInMouth` -> `Ending Orgasmed Inside Mouth`) is invisible to the name matcher and shows up only as a dead folder, and near-spellings that are actually opposites (`Unamused` / `Amused`) are refused by an explicit negation guard. Docs: `docs/packs/checking.md`.
- Voice categories are **strings that must match AudioUtil folder names / TOML keys** — the `AllFemale/AllMaleCategories` tables in `SLOVE_VoiceCategories.psc` are the source of truth (audit with `SLOVE_Test.AuditVoicePack`).
- **`debugtext` IS the Variation-B folder name, and a call site that repeats the A name silently loses the pack.** `SLOVE_Voice.PlaySound`'s per-actor VarB remap swaps `soundToPlay` for `debugtext` only when the two **differ** (and the actor's slot is B and `CategoryExists`). So a call site that passes its own category as `debugtext` has opted out of the remap — fine when the B layout spells that beat the same, silent-failure when it does not. 0.6.15 found three such beats by reading a full scene log (`PenetrativeCommentsIntense` / `-Soft`, `AskForVaginalCum`): the B folders are `Penetrated Comments Intense` / `Penetrated Comments` / `Male Orgasm Soon Ask For Vaginal Cum`, nothing bridged the spellings, and every one of those lines fell past a populated pack folder to the F0/F0B SexLab moans. The bridges live in **`[category_fallbacks.female]`, not `[category_aliases.female]`** — an alias is one hop and dead-ends, a fallback keeps walking the ladder, so a tag-shaped (vD) pack that ships only `Penetrated Comments` and expresses intensity as a *tag* still lands in-pack. They are inert wherever the literal name exists (F0/F0B and the A packs list it; the literal is always tried first). **When you add or rename a beat, check both spellings**, and re-run the audit: every `PlaySound` call site vs a B pack's folder list.
- **Read the voice trace outcome-first; the request half lies.** `SLOVE_Director.TraceVoiceLine` (behind `director.printdebug`) writes one line per voice line to the SLOVE log, ending in `-> <the exact wav AudioUtil played>` from `AudioUtil.GetHandlePath` — ground truth, and the path names the pack folder it came from. It used to print `files=` from `GetCategoryFileCount` instead, which is a **full resolve** (it walks the alias/fallback ladder *and* the fallback-slot chain), so for the 0.6.15 mismatches it reported the F0 stock folder's healthy-looking count while the pack was bypassed entirely — a log of what SLO VE *asked* for cannot catch a resolution bug. `files` survives only on the nothing-played branch, where it still separates "resolves nowhere" from "resolved but the line was dropped" (scene-end stop, duck, busy channel). `CurrentSceneName` is cached per scene change so the line can name the animation without a registry lookup per call. For the layer below this — which tag *pool* answered, whether the pick descended to a lower one, and why a line played nothing — use AudioUtil's own `autest voicelog player` (0.9.20+); no Papyrus native exposes pool tags.
- **External mute events (0.6.27, untested in game) - the inbound half of the `SLOVE_*` event API.** `akActor.SendModEvent("SLOVE_Mute_Stage" | "SLOVE_Mute_Scene" | "SLOVE_Unmute_Stage" | "SLOVE_Unmute_Scene", "<caller name>", face)`: sender = the actor, strArg = the calling mod's name, numArg >= 1 = also hand over the face. Built for SexLab Snuff (which mutes its strangle victim through SexLab's own voice, invisible to AudioUtil) after a first attempt that read that mod's private StorageUtil keys was thrown away - never couple SLO VE to another mod's internals, give it an event. **Design: a mute is never swept or cleared when it runs out - it is time-stamped and judged on read.** The first version cleared mutes from the Director's `StageStart` / `AnimationStart` / `AnimationEnd` handlers by comparing the thread's own scene/stage state, and two code reviews took it apart: P+ sends `StageStart` BEFORE it advances the stage, the muting mod answers the same events in either order, `StartedAt` is not reset between runs on P+, and every check-then-clear raced the next mute event. Do not go back to that. Now: `SLOVE_Utils` (shared, the ONLY place the `SLOVE_Mute*` keys are spelled) writes the level plus `Utility.GetCurrentRealTime()` on the actor (`SetMute` / `LiftMute`), and `MuteLevel(actor, threadId)` judges it against per-thread marks the Director sets for EVERY SexLab thread: `MarkSceneEnd` (AnimationEnd, and `DirectorEndScene`'s poll path); `MarkSceneStart` (AnimationStarting + AnimationStart, idempotent per scene; copies the last scene end into the **floor**, which then stays put until the next scene starts, so a scene's own end never turns its mutes off under the engines tearing it down); `MarkStageStart` (StageStart; classic also AnimationChange - the scene's FIRST stage start is recorded apart and is not a boundary, because classic sends AnimationStart seconds before it). A mute counts only if it was set on the asking engine's thread and after the floor; a stage mute additionally runs out once a later stage has started, with `MuteGrace()` (2s) on BOTH sides of that start: before it, so a mute re-sent in answer to `StageStart` wins whichever handler runs first; after it, so the outgoing mute covers the gap until the re-sent one lands. `threadId = -1` means "the actor resolves to no thread any more" (on P+ an ending thread no longer answers `GetThreadByActor`): the mute is then judged on its own thread and also against that thread's last scene end - that is how the voice gate stays shut for an end-of-scene climax cry. Real time restarts with the game, so `Maintenance` calls `SLOVE_Utils.ClearMutes()` (bulk clear of the `SLOVE_Mute` prefix - **every key of this feature must keep that prefix**) as its FIRST step after opening the log. Gates: `SLOVE_Director.PlaySound` is the one door every voice line leaves through, so the gate is there (`MuteWritten` first - two natives - and the thread lookup only when something is written); `SLOVE_Voice.PlaySound` asks earlier too, only to spare its ducking and waits. `SLOVE_Expressions.OnUpdate` rides the external-ahegao yield on level 2 and latches `FaceHandedOver` (cleared only when the mute is lifted while the scene still runs), which is what `resetexpressions` reads so a death face survives teardown; the yield branch runs the same `SceneGone()` test as `FullExpressionPass`, because it returns before it and a face mute holds it for whole scenes. `DirectorOnMute` cuts the actor's in-flight line by stopping its channel (`SLOVE_Utils.VoiceChannel`, the one spelling of the channel names, plus the `_orgasm` lane) - and deliberately does NOT call `AudioUtil.StopLipSync`: that is a hand-back that freezes the mouth mid-shape, while a stopped line makes AudioUtil fade it shut. SexLab's own silence (`SuppressSexLabVoice`) is re-asserted on every tick while `SLOVE_Utils.MuteJustLifted()` - 4s after any unmute, and after any stage start once a mute has been written this session (a stage mute can run out there with no event) - in the Director and in `SLOVE_NpcScene`, because a mod that restores SexLab's voice with ForceSilence off drops ours; actors with a mute in force are skipped. The `SLOVE_MutedActors` form list is an index for `slovetest mutes` and `MutedCount` only - nothing that decides a mute reads it, and a mute that ran out stays written (and listed) until it is lifted or the game is loaded. Known soft spot: a lost `AnimationEnd` on a non-player thread lets a scene mute into that thread's next scene for the same actor. Classic's `ActorThreadID` looks past a finished thread (its Frozen state keeps the positions for ~10s and `GetActorController` returns the first slot holding the actor). Console: `slovetest mute|unmute <stage|scene> [face]`, `slovetest mutes`. Docs: `docs/authors/integration.md`.
- **A setting lives in four places (since 0.7.0): add or change them together.** (1) the script read, `SLOVE_Config.Get*("section.key", fallback)`; (2) the shipped line in `dist\SKSE\Plugins\SLOVE\SLOVE.toml`; (3) its `[[setting]]` in `SLOVE_Menu.toml` (page, group, label, control, tooltip; no DLL rebuild needed); (4) its row in `docs\config\slove.md`, whose Default cell must equal the shipped value. `scripts\check-config.ps1` (run first by every build) names whichever is missing. The tooltip must not state the default (the menu adds it from `SLOVE.defaults.toml`), and the schema is ASCII only.
- **A new volume bus = `skse\src\Bridge.cpp` too.** The menu moves volumes live by mirroring the key -> bus table the scripts apply at scene start (`SLOVE_Voice`, `SLOVE_NpcScene`, `SLOVE_SFX`), including the two fallbacks (`orgasmvolume` -> `pcvolume`, `npcscenevolume` -> `partnervolume` while the key is not in the file). `check-config.ps1` compares the bus names and the "Applies at once" tooltips against that table.
- **When a changed setting takes effect.** Each engine reads its keys when its effect starts on an actor, and the Director's cached block (`InitializeDirectorConfigs`: `director.*`, `milk.*`, the `resistance.enable*` gates, `sfx.enable`) is re-read on game load, at every player scene start and, since 0.7.0, at the start of an NPC-only scene while no player scene runs (`TryAdoptNpcScene`; skipped during a player scene because the refresh writes `milkenable` twice and that scene's update loop reads it). So "from the next scene" is the promise the menu makes, and it holds for both scene kinds.
- **No HUD bar in SLO VE: willpower is shown by SL Widgets (decided 2026-10-08).** A bar on TrueHUD's special bar was built in `SLOVE.dll` and removed the same day (commit `c3deb17` and the one after it): TrueHUD has ONE special bar for all plugins, which stun and poise meters hold, and the user moved the display to SL Widgets (an iWant Widgets meter with an icon, in the `slwidgets` repo). SLO VE's part is the StorageUtil contract on the `SLOVE_Resistance` row above, nothing else. Do not bring a bar, a TrueHUD dependency or willpower mod events back into this repo without being asked.
- **Windows Defender can block `scripts\check-config.ps1` after an edit.** AMSI judges the whole script text and has refused it as "malicious content" (`ScriptContainedMaliciousContent`, the build dies in its first step) over a harmless added line (a second `Fail "... (sha256 ...)"`). When that happens the last edit to the script is the cause; wording the line differently cures it.
- **Two logs are named SLOVE.** `SKSE\SLOVE.log` is the plugin's (menu only); `Logs\Script\User\SLOVE.0.log` is the scripts' (`SLOVE_Log`). Say which one in docs and bug reports.
- Live config reload in-game: `sloveconfig reload` (SLOVE.toml; the menu does it by itself after each write) and `au reload` (voice slots).
